# Foodster Delivery Management Platform

> **Fullstack-приложение для операционной команды платформы доставки еды Foodster.**  
> Разработано по ТЗ с соблюдением строгих инженерных стандартов: чистая архитектура, конечный автомат статусов (FSM), Optimistic Concurrency Control (OCC), защита от race conditions, триграммный нечеткий поиск и эргономичный B2B-интерфейс без визуального шума («нейрослопа»).

## Быстрый старт

### Требования
* **Node.js** `>= 20.x` (проверено на Node.js v22/v26)
* **npm** `>= 10.x`
* **Docker & Docker Compose** (опционально: если Docker запущен, проект автоматически использует контейнер PostgreSQL 16; если Docker выключен, проект бесшовно использует встроенный изолированный движок PostgreSQL с сохранением данных).

---

### 1. Установка зависимостей
```bash
npm install
```

### 2. Запуск и настройка базы данных
```bash
# Поднимает PostgreSQL в Docker (при наличии) и накатывает миграции со сидами (20 ресторанов, 20 курьеров, 200 заказов)
npm run dev-db:setup
```

### 3. Запуск приложения для разработки
```bash
# Запускает одновременно Backend (порт 3001) и Frontend (порт 3000)
npm run dev
```

После запуска откройте в браузере:
* **Frontend:** [http://localhost:3000](http://localhost:3000)
* **Backend API Health:** [http://localhost:3001/api/health](http://localhost:3001/api/health)

---

### 4. Запуск тестов
```bash
# Настройка тестовой БД (при необходимости)
npm run test-db:setup

# Запуск полного набора интеграционных тестов
npm run test
```

## Ключевые инженерные решения

### 1. FSM жизненного цикла заказа
Жизненный цикл заказа управляется строгим конечным автоматом:

```text
[ new ] ──> [ accepted ] ──> [ preparing ] ──> [ ready ] ──> [ picked_up ] ──> [ delivered ]
   │             │                 │              │
   └───► [ cancelled ] ◄───────────┴──────────────┘
```

* **Правило отмены:** заказ можно отменить только **до** передачи курьеру (до статуса `picked_up`). Как только заказ перешел в `picked_up` или `delivered`, любая попытка отмены отклоняется с ошибкой HTTP `422 Unprocessable Entity` (`BUSINESS_RULE_VIOLATION`).
* **Запрет обратных и перескакивающих переходов:** переход из `new` напрямую в `delivered` или возврат из `ready` в `accepted` блокируются валидацией автомата.

---

### 2. Optimistic Concurrency Control (OCC)
В реальной операционной работе два сотрудника могут одновременно открыть один и тот же заказ:
1. Заказ содержит целочисленную версию `version INT NOT NULL DEFAULT 1`.
2. При открытии заказа клиент получает текущую версию.
3. При любой мутации (смена статуса, назначение курьера, отмена) клиент передает версию в теле запроса.
4. Обновление в БД выполняется атомарно:
   ```sql
   UPDATE orders
   SET status = $new_status, version = version + 1, updated_at = NOW()
   WHERE id = $id AND version = $requested_version
   RETURNING *;
   ```
5. Если строки не обновлены (версия изменилась), сервер возвращает HTTP `409 Conflict`:
   ```json
   {
     "statusCode": 409,
     "error": "Conflict",
     "code": "CONCURRENCY_CONFLICT",
     "message": "Конфликт версий: заказ был изменен другим оператором."
   }
   ```
6. **Поведение фронтенда:** UI отображает предупреждающий баннер и моментально инвалидирует кэш React Query, подгружая свежее состояние без потери фокуса оператора.

---

### 3. Лимит активных доставок курьера (Max 3)
* **Бизнес-правило:** Один курьер не может иметь более **3 активных доставок одновременно**.
* **Определение активных доставок:** Заказы в статусах `ready` и `picked_up`.
* **Защита от состояния гонки (Race Condition):**
  Операция назначения курьера выполняется внутри транзакции с блокировкой строки курьера:
  ```sql
  -- Блокируем запись курьера на время проверки, исключая одновременное назначение в параллельных потоках
  SELECT * FROM couriers WHERE id = $courier_id FOR UPDATE;

  -- Считаем текущие активные заказы курьера
  SELECT count(*) FROM orders
  WHERE courier_id = $courier_id
    AND status IN ('ready', 'picked_up')
    AND id != $current_order_id;
  ```
  Если количество `>= 3`, транзакция прерывается с ошибкой HTTP `422`.

---

### 4. Audit Log (Аудит всех изменений)
Каждое действие оператора или системы протоколируется в таблице `order_audit_logs`:
* Поля: `order_id`, `action_type`, `old_status`, `new_status`, `courier_id`, `details`, `created_at`.
* Записи создаются в той же ACID-транзакции, что и сам апдейт заказа.
* В карточке заказа оператор видит полную хронологическую ленту событий.

---

### 5. Поиск по адресу с опечатками (PostgreSQL pg_trgm)
Для быстрого и умного поиска оператором по неточным адресам подключено официальное расширение PostgreSQL `pg_trgm`:
* На поле `delivery_address` создан GIN-индекс:
  ```sql
  CREATE INDEX idx_orders_address_trgm ON orders USING gin (delivery_address gin_trgm_ops);
  ```
* Поиск выполняется по условию с экранированием спецсимволов LIKE:
  ```sql
  delivery_address ILIKE '%query%' ESCAPE '\\' OR similarity(delivery_address, query) > 0.2
  ```
* Оператор может ввести «*Новаслобоцкая*», и система корректно найдет заказ на «*Новослободская улица*».

## UI/UX дизайн: анти-нейрослоп и инфо-минимализм

Интерфейс спроектирован по канонам B2B-инструментов (Linear / Apple Pro / AtlasCRM):
1. **Никаких эмодзи:** Вместо эмодзи используются аккуратные векторные SVG-иконки `lucide-react` с единым `strokeWidth={1.5}`.
2. **Никакого «нейрослопа»:** Отсутствуют псевдо-AI плашки со искрами, градиентные переливы, неоновые тени и агрессивный капс `uppercase tracking-[0.2em]`.
3. **Информационная плотность:** Компактная таблица со статусами, быстрые фильтры с клавиатурной доступностью, отсутствие дублирования одних и тех же полей.
4. **Статусы с понятной семантикой:** Спокойные фоновые плашки с точечными индикаторами цвета (нейтральный slate для нового, теплый amber для готовки, изумрудный для готовности, фиолетовый для курьера в пути, зеленый для доставленного, мягкий rose для отмененного).
5. **Предотвращение ошибок на клиенте:** В выпадающем списке курьеров отображается их текущая нагрузка (`Иван (2/3 доставок)`). Если у курьера 3/3 активных доставок, выбор блокируется еще до отправки запроса.

## Использование AI-инструментов (AI Disclosure)

В соответствии с правилами задания, открыто декларируем использованные AI-инструменты:

### 1. Какие инструменты использовались:
* **Google Antigravity IDE (Gemini 3.8 Flash & Claude)** в режиме парного программирования.

### 2. Для каких частей задачи использовался AI:
* **Генерация сид-данных и моков:** Быстрое создание реалистичных списков из 20 ресторанов, 20 курьеров, 200 заказов и 820 связанных аудит-логов с правдоподобными таймстемпами и адресами.
* **Рутинный бойлерплейт:** Быстрая генерация типизированных Zod-схем, Tailwind CSS разметки скелетонов и конфигурационных файлов сборщика.
* **Написание интеграционных тест-кейсов:** Покрытие граничных случаев Vitest по спецификации ТЗ.

### 3. Что проектировалось и реализовывалось под строгим контролем:
* **Архитектура изоляции транзакций:** Решение проблемы Race Conditions через пессимистическую блокировку строки курьера `FOR UPDATE` внутри транзакции.
* **FSM матрица:** Строгие правила допустимых переходов и точка невозврата отмены заказа (`picked_up`).
* **Optimistic Concurrency Control:** Контракт обработки конфликта одновременного редактирования и инвалидации кэша TanStack Query на фронтенде.
* **PostgreSQL pg_trgm:** Выбор триграммных индексов GIN для отказоустойчивого поиска с опечатками.
* **UI/UX контроль:** Зачистка нейросетевых клише, поддержание чистого B2B стиля интерфейса.
